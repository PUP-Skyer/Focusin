# 聚光 FocusIn · 消息智能体聚合平台

## 项目功能规划需求文档

| 项 | 内容 |
|---|---|
| 项目名称 | 聚光 FocusIn |
| 参赛赛道 | LifeHack 生活娱乐 |
| 产品形态 | 桌面端（主）+ Web 端（伴） |
| 开发周期 | 首个可演示 Demo：3 天；完整版本：1 个月内 |
| 文档版本 | v1.5（2026-11-26） |

> 聚光：聚合消息，聚焦要事。不是让你看更多消息，而是让你少看消息。

---

## 1. 项目背景与问题定义

### 1.1 痛点

打工人的日常沟通被切分在五六个互不打通的应用里：客户和项目群在微信，部门通知在钉钉，协作在飞书，行业交流在 QQ 群和抖音群，正式函件在邮箱。一个职场人典型的一天是这样度过的：

- **漏看**：8 个群共 200+ 条消息，领导的关键指示被表情包和闲聊淹没；
- **错过**：客户约的会议时间藏在邮件正文第三段，或者某个钉钉群的某条消息里；
- **重复切换**：为了确认一件事，在 4 个应用之间来回翻找，下班时"好像什么都没干，但一直在看消息"；
- **无法检索**："领导上周在群里说的报销新流程到底是什么？"——没有任何工具能跨应用回答这个问题。

这是**消息过载导致的信息整理失能**：不是没有消息，而是消息多到无法被整理成待办、日程与知识。

### 1.2 现有方案的空白

| 方案类型 | 代表 | 缺什么 |
|---|---|---|
| 多合一客户端 | Franz、IM+ | 只做界面聚合，不做语义处理；不支持国内主流 IM |
| AI 助手 App | 豆包、Kimi | 聪明，但不知道你的群聊和邮件里有什么——没有消息上下文 |
| 邮件客户端 | Outlook、Foxmail | 只覆盖邮箱，摘要与日程提取能力弱 |
| 企业协作平台 | 飞书、钉钉本身 | 只覆盖自家生态，管不住微信里的客户群 |

**空白点即定位**：没有任何一款产品同时做到"聚合国内主流 IM + 邮箱的消息"、"用 AI 做分诊摘要和日程提取"、"让智能体直接以消息为上下文替用户干活"。

### 1.3 目标用户

- **主画像：消息过载的职场人**——运营、市场、项目经理等"多群多线"岗位，同时维护客户群、部门群、项目群，需要在闲聊噪音里抓住待办与指示；
- 次画像：学生组织骨干/研究生——社团群、课程群与老师/导师指示分散多端，同样需要分诊与整理（衔接赛道"生活、社团场景"）；
- 次画像：多群生活的普通人——家人群、业主群、孩子班级群消息淹没，既没时间提取也没精力检索当日日程与通知，"打开即答案"是唯一解；
- 次画像：求职/多线沟通的过渡期人群——邮件与群聊双线作战，面试时间散落各处；
- 次画像：小微团队负责人——既是消息的接收者又是分发者，需要把散落的指示整理成行动项。

## 2. 产品定位与范围

### 2.1 一句话定位

**本地优先的消息聚合 + AI 分诊 + Agent 执行平台**：把微信、QQ、飞书、抖音群聊、钉钉和邮箱的消息汇于一处，智能体以这些消息为工作上下文，在平台内直接完成摘要、排程、检索与起草——全程不跳转任何页面。解决工作人群消息太多、无法整理的问题。

### 2.2 范围边界

- 本文档覆盖**功能需求 + 系统架构**，不含商业化设计与详细排期；
- 桌面端承载全部能力（含本地化渠道接入与本地数据）；Web 端为轻量伴侣（远程查看摘要、日历与对话）；
- 功能按 P0/P1/P2 分级，P0 为"消息汇总 + 日程 + Agent 对话"最小闭环。

### 2.3 成功标准（P0 闭环演示路径）

> 收到 50 条群消息 → 平台生成 3 行分诊摘要 → 从中提取 1 个日程事件并落库提醒 → 用户在对话框说"帮我起草一条回复" → 智能体检索上下文后给出草稿。全程零页面跳转。

### 2.4 核心差异化（相对通用 ChatBot 套壳）

1. **"消息即上下文"范式**：智能体直接以聚合消息为工作记忆——这是与"通用助手套壳"的本质区别；
2. **可解释的 AI 安全防线**：每一步工具调用有风险分级、可审批、可拦截，机制全部有可指认的开源设计出处；
3. **分层合规接入**：不回避微信/QQ 的现实难题，用"正门 + 实验旁门 + 随时可关"的架构把合规问题转化为设计能力。

## 3. 用户场景与故事

### 场景一：职场人的晚间十分钟

- **当前做法**：逐个群往上翻 30 分钟，边翻边截图记待办，还是漏了客户在微信群里要的改稿需求。
- **平台做法**：晚上打开聚光，看到全天 8 个群的分诊摘要——"待办 3 / 日程 2 / 重要 1"，其中"明早十点前给客户发 v2 方案"已自动进入待办清单，附原文跳转定位。

### 场景二：散落各处的会议时间

- **当前做法**：客户邮件里一场、钉钉群里一场，时间全靠手动抄进日历，抄漏一场就是放一次鸽子。
- **平台做法**：平台从邮件正文和群聊通知中分别提取出两场会议，生成日历事件前展示"原文依据"供确认，双提醒（提前 1 天 + 提前 1 小时）自动生效。

### 场景三："领导到底说过啥"

- **当前做法**：翻遍微信、邮件、飞书，凭记忆拼凑领导上周关于报销新流程的指示。
- **平台做法**：在对话框输入"领导上周关于报销说了什么？"——智能体检索跨渠道历史消息，给出带出处的汇总，并起草一条可直接粘贴到工作群的确认消息草稿（只起草，发送由用户自己完成）。

### 场景四：学生组织骨干的社团群

- **当前做法**：社团群、课程群、通知群各一个，策划案截止时间被刷屏的闲聊淹没，还要切去邮箱确认场地申请结果。
- **平台做法**：分诊摘要把"周五前交策划案"自动归入待办四象限，场地申请邮件的回复自动进入重要组；老师在群里 @ 自己的指示，可以让 Agent 一键整理成行动项清单。

### 场景五：普通人的"今天到底有什么事"

- **当前做法**：家人群、业主群、孩子班级群、老同学群全是消息，谁 @ 了自己不知道；明天孩子家长会的时间藏在班主任发的长消息中间，想翻没精力翻，想搜不知道从哪搜——最终靠错过和挨骂来发现。
- **平台做法**：打开纵览页即见答案——"今日聚光"横幅一句话说清今天有几件事；家长会时间已被提取到日历（附原文出处可核对），待办与日程分列卡片；**不需要任何检索动作，打开就看完**。

## 4. 功能需求总览

### 4.1 模块地图与优先级矩阵

| 模块 | 名称 | P0 | P1 | P2 |
|---|---|---|---|---|
| M1 | 统一渠道接入 | 飞书/钉钉/邮箱 | 微信/QQ/抖音本地化只读 | SMTP、Telegram、企微、配对码绑定 |
| M2 | 智能分诊与摘要 | 会话摘要 + 五分组分诊 | 每日简报 + 链接自动摘要 | 摘要风格个性化 |
| M3 | 日程提取与日历 | 防幻觉日程提取 + 提醒 | 消息 RAG 检索 + 四象限待办 + 农历 | .ics 订阅、双向同步、版本历史 |
| M4 | Agent 对话与执行 | 多模型对话 + 平台内工具 | Plan 模式 + 定时自动化 | 纪要生成、多 Agent、SKILL、语音输入 |
| M5 | 安全与审批（横切） | 风险分级 + HITL + 脱敏 | taint 追踪 + 密钥保险库 | — |
| M6 | 记忆与个性化 | — | — | 记忆文件制 + 风格学习 |
| M7 | Agent 形象 IP 化 | — | 萌系形象 + 性格设定 | 形象动画 |
| M8 | 任务中心与用量统计 | — | 任务透明可中断 | token 用量统计 |
| M9 | 消息可视化 | — | 词云/思维导图/关系图谱 | 对话驱动生成 |
| M10 | 笔记收藏与周报 | — | 一键收藏 + 笔记 | AI 续写 + 周报导出 docx |

### 4.2 三天 Demo 交付范围与裁剪原则

首个 Demo 需在 **3 天内可演示**，范围从 P0 进一步收窄为"单渠道 + 邮箱的最小闭环"，并采用演示数据集兜底：

| Day | 交付目标 |
|---|---|
| Day 1 | 本地服务进程 + SQLite 数据模型 + 飞书（或钉钉）官方 API 长连接接入 + IMAP 邮箱水位拉取；导入一份**模拟工作消息数据集**（8 群 × 200 条，含待办/日程/闲聊混合）作为兜底演示数据 |
| Day 2 | 分诊摘要管道 + 日程提取（提示词锁定工具 + 原文依据确认）+ 日历视图与提醒；Agent 对话框 + 多模型 SSE + 工具注册表（消息检索/日程 CRUD/草稿起草） |
| Day 3 | HITL 审批弹窗与脱敏（安全线最简版）+ 前端交互打磨（分诊动画、首页信息流）+ 演示彩排与异常兜底（断网演示走本地数据集） |

裁剪原则：

- Demo 期渠道接入只做 **1 个官方 API 渠道 + 邮箱**；微信/QQ/抖音用模拟数据集演示产品效果，接入能力留到完整版（架构上已预留 Channel 插件位）；
- 所有 P1 功能不得阻塞 Demo 闭环：每个模块有独立降级路径（如实时接入失败立即切演示数据集）；
- P2 仅写入文档与架构预留（接口占位），不承诺实现；
- 完整版在 Demo 后按 P0 补齐 → P1 增强的顺序推进，1 个月内完成。

### 4.3 前端交互娱乐化设计原则

赛道二的产品气质靠交互层而非功能层传达：

- 消息入站、分诊完成、日程提取等关键节点有**轻量动画反馈**（涟漪、徽章弹跳）；
- 助手形象（M7）在对话中有表情与待机动作，拒绝"工作软件脸"；
- 可视化图表（M9）默认采用趣味配色与萌系图标，生成物可一键导出分享图片；
- 整体 UI 遵循生活娱乐产品的轻松基调，弹层文案口语化、有温度。

## 5. 核心功能模块详述

### M1 统一渠道接入

**目标**：所有渠道的消息以统一模型汇入平台，渠道差异对上层透明。

| 功能点 | 级别 | 说明 |
|---|---|---|
| Channel 适配器框架 | P0 | 统一基类（start/stop/send），渠道实现只关心协议细节；新渠道即插件 |
| 飞书/钉钉接入 | P0 | 官方开放平台 API，出站长连接，无需公网 IP 与内网穿透；机器人凭证由用户自行申请 |
| 邮箱接入 | P0 | IMAP 收件，UID 水位式增量拉取（首连只记水位不回放历史），支持 QQ 邮箱/Gmail/Outlook 等主流服务商 |
| 统一消息模型与会话映射 | P0 | 每条消息标准化为 `{渠道, 会话ID, 发送者, 时间, 文本, 附件}`，按 `渠道:会话ID` 映射到平台内会话，消息级去重键防重复入库 |
| 微信/QQ/抖音本地化接入 | P1 | 桌面端本地自动化方式，**只读优先**（详见第 10 章合规声明），标记为实验性插件；技术路线参考 nanoMuse Hands（截屏感知 + UI 操作，源自 UI-TARS）与系统无障碍接口 |
| 发送能力 | P2 | SMTP 发件；Telegram/企微渠道 |
| 渠道绑定配对码 | P2 | 新渠道绑定需配对码/扫码验证，防止凭证被伪造或陌生人恶意绑定 |

**验收标准**：
1. 飞书群里发一条消息，3 秒内出现在平台消息流中；
2. 断网 10 分钟后恢复，渠道自动重连并按水位补拉期间邮件，无重复入库。

> 设计参考：EvoFlow `backend/app/channels/base.py`（Channel 基类 + 消息总线）；nanoMuse `nanomuse/triggers/mail.py`（IMAP 水位式增量）。

### M2 智能分诊与摘要

**目标**：让用户"少看消息"，而不是"看更多消息"。

| 功能点 | 级别 | 说明 |
|---|---|---|
| 会话级摘要 | P0 | 按渠道-会话聚合，生成 1-3 行要点摘要，附关键原文定位 |
| 五分组分诊 | P0 | 每条消息分入：待办 / 日程 / 通知 / 重要 / 闲聊；前四组进首页信息流，闲聊默认折叠 |
| 链接自动摘要 | P1 | 消息中的文章/公告链接自动抓取正文（Readability 提取正文，只读操作免审批），生成一行摘要附在消息卡片上——不点开链接就知道内容 |
| 附件解析 | P2 | 邮件附件与群文件（docx/pdf/xlsx 等）自动解析为文本，进入消息内容与 RAG 索引——"群里发的那个通知 PDF"也能被搜到 |
| 每日简报 Morning Feed | P1 | 每天早上 8:00 生成"昨日摘要 + 今日日程 + 待办清单"三段式简报，桌面通知推送 |
| 摘要风格个性化 | P2 | 学习用户偏好（简洁/详细/带表情），由记忆模块（M6）支撑 |

**验收标准**：
1. 50 条混合消息生成摘要耗时 < 15 秒（P95）；
2. 五分组分诊中"待办"识别准确率 ≥ 80%（人工标注 100 条验证）。

> 设计参考：nanoMuse `skills/builtin/inbox-triage`（五分组分诊、只起草不代发）；EvoFlow proactive（主动汇报/值班产出）；Happy Friday Lite `fetch_webpage_text` 工具（Readability 正文提取）。

### M3 日程提取与日历

**目标**：日程从消息里"长"出来，且绝不允许编造。

| 功能点 | 级别 | 说明 |
|---|---|---|
| 提示词锁定的日程提取 | P0 | 模型被约束为只能调用日程 CRUD 工具（list/create/update/delete），禁止在回复中"宣布"创建成功——工具返回成功才算完成；提取结果必须附原文依据供确认 |
| 日历视图 | P0 | 月/周视图 + 当日列表，日程事件可溯源到原消息（点击跳到原文上下文） |
| 提醒机制 | P0 | 提前 N 分钟 + 到期双提醒；5 分钟补发窗口防应用重启漏提醒；去重键防重复推送 |
| 四象限待办视图 | P1 | 待办按重要/紧急四象限组织，一眼看清优先级；日历支持农历显示，贴合国内生活节奏 |
| 消息 RAG 语义检索 | P1 | 历史消息建向量索引（父子分块策略，新消息增量索引），支持"领导上周说啥了"式跨渠道自然语言检索，返回带出处的原文；中文检索采用 bigram 关键词 + 向量语义混合召回，兼顾准确与语义泛化 |
| 日历订阅与同步 | P2 | .ics 订阅导出；飞书/钉钉日历双向同步 |
| 日程版本历史 | P2 | 日程/待办的修改历史与差异对比，Agent 误改可一键回滚 |

**验收标准**：
1. 从"周四晚 7 点例会，别迟到"一条群消息提取出日程事件并正确落库，展示原文依据；
2. 对含糊表述（"下周 sometime 聚餐"）模型主动追问而非强行创建。

> 设计参考：Happy Friday Lite schedule 模块（提示词锁定工具 + schedule_events 表 + 双提醒/补发窗口/去重键）、四象限组件与农历（`ScheduleQuadrant.vue`、`lunarCalendar.js`）、知识库模块（父子分块 + 增量索引）与笔记版本历史；nanoMuse `calendar/feeds.py`（.ics）。

### M4 Agent 对话与执行

**目标**：平台内一个对话框 = 一个能干的私人助理，不跳转任何页面。

| 功能点 | 级别 | 说明 |
|---|---|---|
| 多模型接入 | P0 | OpenAI 兼容 API，SSE 流式输出；支持 DeepSeek/通义千问/Kimi/豆包/智谱等，用户填自己的 Key；按供应商差异化适配推理（thinking）开关 |
| 工具注册表 | P0 | 统一 `registerTool({ name, description, schema, handler, meta })` 模式，Zod schema 描述参数，meta 声明风险等级；工具对模型以中文描述用途与副作用 |
| 平台内工具集（P0） | P0 | 消息检索（按渠道/会话/关键词/时间过滤）、日程管理（CRUD，复用 M3）、邮件起草（只产出草稿）、群通知草稿（生成文本，由用户手动粘贴或经审批发送） |
| Plan 模式 | P1 | 复杂任务先产出可修订的分步计划，用户确认后逐步执行，进度实时回显 |
| 定时自动化 | P1 | 用户自定义定时任务（如每日 22:00 摘要推送），SQLite 存储、分钟对齐调度、漏跑补偿、多进程幂等锁 |
| 文档生成 | P2 | 群聊消息一键生成会议纪要/活动周报文档（Markdown 导出）；多 Agent 协作（调度者-执行者分工） |
| SKILL 技能包 | P2 | Markdown 技能文件扩展 Agent 能力（如"报销流程话术""会议纪要模板"），可安装、可分享 |
| 语音输入 | P2 | 对话框支持语音输入转文字，通勤路上口述指令 |
| 长对话上下文压缩 | P2 | 会话过长时自动压缩早期上下文，长任务不清空重开（上下文压缩器） |

**验收标准**：
1. 对话首字响应 < 3 秒（SSE）；
2. "帮我把宣传部群里关于海报的要求整理成待办"——智能体调用检索工具，返回带出处的整理结果，全程平台内完成。

> 设计参考：Happy Friday Lite `src-electron/agent/tools/registry.js`（工具注册 + schema + meta）与 `llm.js`（多供应商 SSE 适配）；EvoFlow Plan/Goal（调度者-执行者循环 + 显式终止信号）与自动化调度（tick/补跑/幂等锁）。

### M5 安全与审批（横切所有模块）

**目标**：智能体能干活，但每一步可拦。

| 功能点 | 级别 | 说明 |
|---|---|---|
| 工具风险分级 | P0 | 每个工具静态声明 safe / moderate / sensitive；运行时按参数动态升级（如检测到支付、删除关键词） |
| HITL 审批 | P0 | sensitive 工具调用前弹审批卡（展示工具、参数、风险说明），用户可批准/拒绝/修改；审批作用域：本次 / 本会话 / 24 小时 / 始终允许 |
| 敏感信息脱敏 | P0 | 验证码、OTP、重置链接等进入模型上下文前自动打码；用户自行输入的密码/验证码永远不出现在模型输入中 |
| 邮件"只起草不代发" | P0 | 邮件类外发动作默认只生成草稿，发送必须由用户在界面显式点击 |
| taint 追踪 | P1 | 智能体读取过私密数据后，其后续外发动作（HTTP 请求、邮件）强制升级审批，防注入外泄 |
| 密钥保险库 | P1 | API Key 以 `{{vault:NAME}}` 占位符形式进入提示词，明文永不出现在日志与模型输入 |

**验收标准**：
1. 任何一次邮件发送尝试都会被拦截并展示审批卡；
2. 日志全量审计可查：每次工具调用的时间、参数、风险评级、审批结果。

> 设计参考：nanoMuse Sentinel（`nanomuse/sentinel/`，风险分级 + taint + 审计）；Happy Friday Lite `humanInTheLoop.js`（interrupt → IPC 弹窗 → resume 恢复）。

### M6 记忆与个性化（P2）

记忆文件制：用户偏好、常用话术、汇报风格存为本地 Markdown 文件（人格/用户画像/长期记忆/经验四文件），智能体可自主更新；LLM 定期整理合并，全程留变更日志可撤销；摘要与简报据此学习个人风格。记忆注入系统提示词时设置 **token 注入预算**，避免记忆挤占消息上下文。

> 设计参考：Happy Friday Lite `/memories/` 四文件制；nanoMuse 记忆库（分类词条 + 变更日志）。

### M7 Agent 形象 IP 化（P1）

- 助手有名字与默认萌系形象（如小信鸽），用户可上传或用图像模型生成自己的形象；
- 形象在对话与通知中出现（待机、思考、完成任务三种状态表情）；
- 性格设定可编辑（话痨/高冷/毒舌），影响摘要与回复的语气。

> 设计参考：nanoMuse 形象生成（图像模型画形象、视频模型使其动）。

### M8 任务中心与用量统计

| 功能点 | 级别 | 说明 |
|---|---|---|
| 任务中心 | P1 | 后台任务（摘要、索引、定时任务）与工具调用全部可视：状态、耗时、输入输出；可中断、可重试 |
| 用量统计 | P2 | 按模型统计 token 消耗与预估费用，支持模型余额查询，帮助用户控制成本 |

> 设计参考：EvoFlow 任务中心/可观测性（任务、工具调用与用量可见）与治理套件（费用统计）。

### M9 消息可视化

|---|---|---|

| 功能点 | 级别 | 说明 |
|---|---|---|

### 6.3 视觉体系

- **双主题**：浅色/深色/跟随系统，全部走 CSS variables；主题选择在首屏渲染前应用，杜绝闪白（nanoMuse 的 `<html data-theme>` 首绘前置方案）；
- **聚光调色板**：白与近黑表面 + **单一暖色品牌色**（区别于 EvoFlow 的企业紫 #635BFF——太"工作"；采用 nanoMuse 式"一个颜色说所有事"的克制用法：品牌色只用于主操作、选中态与运行态）；正文浅灰 #f5f5f5 分层、圆角 10px；
- **token 分层**（借鉴 EvoFlow theme-framework 的 region × surface 契约）：原子变量 → 语义别名 → 区域默认表现，为将来换肤（如"液态玻璃"皮肤）预留通道，不写死颜色；
- **字体**：几何无衬线（Figtree 类）+ 中文回退系统字体栈（PingFang SC / Microsoft YaHei）。

### 6.4 对话与工具调用交互（本产品的门面）

对话流组件分层（全部参考 Happy Friday Lite 的 chat 组件族）：

1. **消息气泡**：用户/助手双气泡，助手侧流式逐字渲染（SSE）；
2. **思考过程**：可折叠的"正在思考…"区，默认收起一行，点开看推理链路；
3. **工具调用段**：状态圆点（运行中呼吸脉冲 → 完成/失败变色）+ 扳手图标 + 一行摘要标题，点击展开参数与返回结果——工具调用对用户透明但不喧宾夺主；
4. **审批弹窗**：顶部警示色条 + 工具信息卡（工具名/参数/风险说明）+ 审批作用域选择（本次/会话/24h/始终），**点击遮罩默认拒绝**（宁拦勿纵）；
5. P2 演进：对话流内**行内审批卡**（参考 nanoMuse `SentinelReviewRow`），不打断阅读位置。

### 6.5 助手形象与情绪（M7 的交互落地）

参考 nanoMuse 的形象系统（`avatars.ts` / `mood.ts`）：

- **六种心情**：待机 idle / 干活 working / 等你确认 waiting / 开心 happy / 出错 error / 断连 sleepy；静态图（webp）打底，视频动画（mp4）在关键状态播放；
- **瞬时情绪反馈**：任务完成开心 3 秒、工具失败担忧 4 秒、服务断连打瞌睡——形象"活着"，这是娱乐化气质的最大来源；
- **形象工坊**：默认萌系形象 + 用户上传或生成自定义形象（AvatarStudio 式编辑器），形象在侧栏头像、对话头像、加载态三处一致出现；
- 待机时形象有轻呼吸动画，审批等待时形象看向审批卡方向。

### 6.7 性能与体验底线

- 首屏只加载首页与对话，其余屏幕懒加载分块（nanoMuse lazy screens 模式）；

- Tooltip 等高频微交互用 DOM 直更而非组件重渲染（Happy Friday Lite 性能细节）。

## 7. 系统架构设计

### 7.1 总体架构：单后端，多前端

核心能力实现为一个**本地服务进程**（Python），暴露本地 HTTP + WebSocket API。桌面端（Tauri/Electron 壳）与 Web 前端（Vue 3）都是它的客户端。P0 阶段 Web 端通过局域网访问本机服务（演示场景：评委用手机扫码打开同一 Wi-Fi 下的页面）；云端中转作为 P2 预留。

```
┌────────────────────────────────────────────────────────┐
│                     客户端层                            │
│  ┌──────────────────┐        ┌──────────────────┐      │
│  │  桌面端（主）      │        │  Web 端（伴）      │      │
│  │  Tauri/Electron  │        │  Vue 3 (Vite)    │      │
│  │  +本地化渠道插件   │        │  摘要/日历/对话    │      │
│  └────────┬─────────┘        └────────┬─────────┘      │
└───────────┼───────────────────────────┼────────────────┘
            │  HTTP / WebSocket（本地服务）
┌───────────▼───────────────────────────▼────────────────┐
│                     本地服务进程（Python）                │
│  ┌──────────────────────────────────────────────────┐  │
│  │ ① 渠道接入层：Channel 适配器（飞书/钉钉/IMAP/本地化） │  │
│  │    出站长连接 · 免公网 IP · 水位增量                │  │
│  ├──────────────────────────────────────────────────┤  │
│  │ ② 消息处理层：MessageBus · 会话映射 · 去重          │  │
│  │    分诊管道 · 摘要生成（三车道隔离，防慢 IO 卡对话）  │  │
│  ├──────────────────────────────────────────────────┤  │
│  │ ③ Agent 执行层：LLM 网关（多供应商）                │  │
│  │    工具注册表 → Sentinel 审批门 → 执行 → 流式回流    │  │
│  ├──────────────────────────────────────────────────┤  │
│  │ ④ 数据层：SQLite（消息/日程/任务/审批/配置/记忆）     │  │
│  │    向量索引（消息 RAG）· 全部本地存储                │  │
│  └──────────────────────────────────────────────────┘  │
│        ═══ 安全层横切：脱敏 · 审批 · 审计 · 密钥保险库 ═══ │
└─────────────────────────────────────────────────────────┘
```

### 7.2 关键架构决策

| 决策 | 理由 |
|---|---|
| 出站长连接，不做入站服务 | 飞书/钉钉官方长连接模式免公网 IP，宿舍/实验室网络环境即可用 |
| SQLite 单库 | 桌面场景最稳选择；消息、日程、任务、审批记录统一管理，全量本地 |
| 三车道请求隔离 | 对话/审批（CONTROL，永不丢弃）与消息拉取、批量索引（BEST_EFFORT，过载可延迟）分道，防止批量任务卡死用户对话 |
| 本地化渠道仅驻桌面进程 | 微信/QQ/抖音接入依赖本机已登录客户端，Web 端自动隐藏这些渠道 |
| 工具调用统一过审批门 | Agent 执行层没有"后门"路径，安全约束在架构上不可绕过 |

### 7.3 P0 闭环时序

```
用户手机            本地服务                飞书服务器         LLM API
   │                  │                       │                 │
   │  (群消息产生)      │◄────长连接推送─────────│                 │
   │                  │标准化+去重→SQLite       │                 │
   │                  │分诊管道 ──────────────────────────────►│
```

## 8. 关键流程时序

### 流程一：消息入站 → 分诊 → 推送

渠道长连接收到消息 → 标准化为统一模型 → 去重键校验 → 入库 → 异步进入分诊管道（五分组 + 摘要）→ 更新首页信息流 → 触达条件（新待办/新日程/重要消息）时推送桌面通知。

### 流程二：对话 → 工具调用 → 执行/审批

用户输入 → LLM 决策（流式）→ 工具调用请求 → Sentinel 风险评估（静态分级 + 参数动态升级 + taint 检查）→ safe 直接执行 / moderate+ 弹审批卡 → 执行结果回流对话流 → 全量审计落库。

## 10. 风险与合规边界

本章采用"分层声明、如实边界、降级路径"三段式，不回避问题。

### 10.1 官方 API 层（完全合规）

飞书/钉钉开放平台、IMAP/SMTP 均为官方授权接口。用户自行注册应用与凭证、自行完成 OAuth 授权，数据范围完全由用户控制。本平台不接触任何账号密码明文。

### 10.2 本地化接入层（实验性，如实声明）

微信、QQ、抖音群聊未向个人用户提供消息开放 API。对该类渠道，本平台采用**桌面端本地自动化方式**接入，定位类比读屏软件与输入法的无障碍辅助：

- 仅读取**用户本人已登录账号**在本机客户端上可见的消息；
- 全部处理在本地完成，不上传、不转发、不存储到任何云端；
- 不破解加密协议、不伪造客户端身份、不用于批量营销或自动化骚扰；
- **如实承认**：该方式存在违反相关平台用户协议的风险，且客户端更新可能导致接入失效。

### 10.3 降级与止损设计

- 本地化渠道为**独立插件**，可一键停用；停用后平台以官方 API 渠道完整运行，核心体验无损；
- 该类渠道**默认只读**，发送类操作默认禁用，开启需二次强确认；
- 渠道接入层抽象保证：任何渠道的异常都隔离在自身适配器内，不影响其他渠道与主流程。

> 我们选择在文档中如实呈现边界，而非回避——这是面向真实用户的产品应有的工程诚实。

## 11. 开放性与展望

- **渠道插件化**：新 IM 只需实现 Channel 基类（start/stop/send）即可接入，架构上向社区共建开放；
- **工具生态**：工具注册表模式天然支持第三方工具包与技能（SKILL）扩展；
- **多 Agent 路线**：从单助理演进为"汇总员、日程管家、检索员"多角色协作（岗位化 + 分级授权），参考 EvoFlow 智能体员工体系；
- **跨设备协同**：远期参考 nanoMuse Hub 协议（单条出站 WebSocket + 审批回传帧），实现"手机上派活、电脑上执行、审批回到手机"。
